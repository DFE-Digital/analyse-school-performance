One of the main aims of ASP 2.0 is for as much of the application as possible to be data driven and not hard-coded. A significant cause many issues in the BAU process is the fact that any new release or any change to a report page, even a simple change to page content would necessitate a development release process. This is because all the pages in BAU are hard-coded within the <span>ASP.NET</span> MVC controllers and views, and each new data release consisted of copying and pasting the controllers and views from the previous year into a new area - the infamous "year-based architecture"!

Previous attempts at deduplicating this copy-pasted code have resulted in a mess of dependencies and shared code with inheritance structures, overridden in various ways as different changes came in from year to year, meaning that every data release requires an engineering team to implement it, preventing a true BAU process where the completed service can be handed off to an operations team.

Key to this vision is the content template engine, effectively a content management system consisting of page templates stored as JSON documents, containing reusable components (tables, charts etc) that can be plugged in and data driven.
